# Research: Production Dump H2 Seed Data

## Decision 1: Selective Table Extraction from Shared Production PostgreSQL Database

- **Decision**: Use `pg_dump --data-only --column-inserts --no-owner --no-privileges` targeting the 9 specific Expense Tracker tables in topological foreign-key order:
  1. `public.categories`
  2. `public.sub_categories`
  3. `public.users`
  4. `public.expenses`
  5. `public.expense_attachments`
  6. `public.expense_comments`
  7. `public.incomes`
  8. `public.income_attachments`
  9. `public.income_comments`
- **Rationale**: The production database (`192.168.1.50:5432/mariasorganicsdb`) is shared with other systems (`bill_*`, `it_*`, `sk_*` tables). Filtering explicitly by table (`-t`) ensures only Mushroom Expense Tracker data is exported. Using `--column-inserts` generates standard `INSERT INTO table (col1, col2, ...) VALUES (...)` statements that are portable to H2.
- **Alternatives considered**:
  - Full database dump: Rejected because unrelated `bill_*`, `it_*`, and `sk_*` tables do not exist in the Expense Tracker JPA schema and would fail on H2 load.
  - CSV export/import: Rejected because multi-table foreign keys and `ResourceDatabasePopulator` work much more cleanly with a single atomic SQL script.

## Decision 2: PostgreSQL-to-H2 SQL Sanitization & Sequence Alignment

- **Decision**: Post-process `pg_dump` output in `scripts/dump-prod-to-seed.sh` to:
  1. Strip PostgreSQL-specific meta-commands (`\restrict`, `\unrestrict`), session settings (`SET ...`), and `SELECT pg_catalog.set_config(...)` / `SELECT pg_catalog.setval(...)` calls.
  2. Strip `public.` schema prefixes (`INSERT INTO public.` -> `INSERT INTO `) so statements execute against H2's default schema seamlessly.
  3. Append H2-compatible identity sequence reset statements for all 9 tables:
     ```sql
     ALTER TABLE categories ALTER COLUMN id RESTART WITH (SELECT COALESCE(MAX(id), 0) + 1 FROM categories);
     ```
- **Rationale**: When explicit IDs are inserted into H2 `GENERATED BY DEFAULT AS IDENTITY` columns, H2 2.x does not advance the internal sequence automatically. Restarting the identity column with `COALESCE(MAX(id), 0) + 1` guarantees zero primary key collisions when new rows are subsequently created via Hibernate/JPA.
- **Alternatives considered**:
  - Hardcoding sequence numbers from `pg_catalog.setval`: Works, but dynamic `SELECT COALESCE(MAX(id), 0) + 1` is self-healing and always accurate in H2.

## Decision 3: Spring Boot Startup Seeding Mechanism

- **Decision**: Enhance `DataInitializer` (using `DataSource`, `ResourceLoader`, and Spring repositories) to check whether the local database is empty (or if `app.seed.force-reset=true` is set in non-prod profiles). When seeding is triggered in non-prod mode:
  1. Check if `classpath:seed/prod-seed.sql` exists and is non-empty.
  2. Execute `classpath:seed/prod-seed.sql` using Spring's `ResourceDatabasePopulator` against the `DataSource`.
  3. Ensure standard dev convenience accounts (`admin`, `manager`, `accountant`, `supervisor`) exist (adding any missing role accounts with default password `password`) so existing manual and automated dev workflows continue to work alongside production users (`admin`, `glen-man`, `liya`, `madhuri`, `glen-sup`).
  4. If `classpath:seed/prod-seed.sql` is absent, fall back to the programmatic seed logic.
- **Rationale**: Using `DataInitializer` (`CommandLineRunner`) guarantees that Hibernate's `ddl-auto=update` has already created/updated all tables before the seed SQL runs, and avoids re-inserting duplicate primary keys when restarting against the persistent file-backed H2 database (`./data/mushroomdb`).
- **Alternatives considered**:
  - `spring.sql.init.data-locations`: Rejected because `application-dev.properties` uses a persistent file-based H2 database (`jdbc:h2:file:./data/mushroomdb`) with `ddl-auto=update`. Running `data.sql` unconditionally on every boot without checking if data is already loaded would fail with primary key constraint violations on the second startup.
